## Guests and snapshots

A group selects **guests**; every guest is one snapshot `plugin-m365-<source>-<guest>`. A group without guests is
refused (a tenant is never backed up as one snapshot).

| Guest id | Object | Snapshot tree (download format) |
|---|---|---|
| `u.<user object id>` | user (members; shared mailboxes are users too) | `mail/<folder>/…/<subject> ~<hash>.eml` (MIME as Exchange returns it) · `calendar/<calendar>/<date> <subject> ~<hash>.ics` · `contacts/<folder>/…/<name> ~<hash>.vcf` · `onedrive/<path>` (files as they are) · `chats/<topic or members> ~<hash>.json` + `.html` (only with **Chats** on) |
| `s.<base64url(site GUID ‖ web GUID)>` | SharePoint site (root web of a site collection on the SharePoint host) | `libraries/<library>/<path>` |
| `t.<group id>` | team | `files/<path>` (the team's document library) · `channel-files/<channel>/<path>` (private and shared channels: their own SharePoint site) · `channels/<channel>/<date> <subject> ~<hash>.json` (thread: root message + replies, Graph JSON) |
| `g.<group id>` | Microsoft 365 group (also the ones behind teams) | `conversations/<topic> ~<hash>.json` (conversation: its threads with their posts, Graph JSON) · `calendar/<date> <subject> ~<hash>.ics` (only if Graph lets the app read it, see "Limits") · `files/<path>` (groups that are not teams; a team's files belong to the team guest) |

Users also get `recoverable/Deletions/<subject> ~<hash>.eml`: the Recoverable Items "Deletions" folder (well-known
folder `recoverableitemsdeletions`, items deleted from Deleted Items), read like any mail folder.

Guest ids follow the contract's rules (`[A-Za-z0-9._-]{1,64}`): user and group ids are GUIDs; Graph site ids
(`host,GUID,GUID`) are too long and contain commas, so the two GUIDs are packed as base64url (45 characters) and the
site id is rebuilt with the configured SharePoint host. ListGuests offers users of type `Member`, all non-personal
sites on the SharePoint host (`/sites/getAllSites`), all teams (`/teams`) and all Microsoft 365 groups
(`/groups?$filter=groupTypes/any(c:c eq 'Unified')`), depending on the enabled workloads.

Tags (auto-protect groups, contract v1.5): `type:user|site|team|group`; `license:none` for users without
`assignedLicenses`; `site:team` for sites a team or group guest already covers — the group's site
(`/groups/{id}/sites/root`) and, for teams, the sites of private and shared channels (`filesFolder` of the channel →
its drive → `sharepointIds` of the drive's root). Groups of mode `all` (and `tags` groups whose selector does not
name the tag) leave guests tagged `license:none` or `site:team` out (`catalog::inventory::DEFAULT_OFF`), so
unlicensed accounts are not backed up by default and no site is backed up twice. Tagging the sites costs one
request per group plus two per private/shared channel in each listing; if Group.Read.All is missing, groups are
skipped with a warning and team sites stay plain sites.

Names: folder and file names are kept; `%`, `/`, ASCII control characters and the names `.`/`..` are
percent-encoded (`Projects/2026` → `Projects%2F2026`), reversed on restore. Items without a natural file name get
`<label> ~<12 hex of SHA-256(id)>.<ext>` so names stay unique and readable. Every directory and file carries its
Graph id in the xattr `user.m365.id`, files their version tag (changeKey / cTag) in `user.m365.tag`.

`.ics` and `.vcf` are generated from the Graph JSON (VEVENT with UID, times in UTC, RRULE for the common
recurrence patterns, attendees, organizer, body as text; vCard 3.0 with names, e-mails, phones, addresses,
organisation, birthday, notes) and carry the complete Graph JSON in an `X-NEXUSBACKUP-GRAPH` property (base64),
which other clients ignore. Restores use that JSON, so they are lossless for every property Graph lets a client
set. Teams threads are stored as Graph JSON (`{"channel", "root", "replies"}`).

## Entra ID setup (once per tenant)

**Helper scripts** (steps 1–3 in one go, run on an admin workstation, never on the appliance):
`plugins/m365/tools/register-app.sh` (Azure CLI `az` + `openssl`; sign in first with
`az login --tenant <tenant> --allow-no-subscriptions`) or `plugins/m365/tools/register-app.ps1 -TenantId <tenant>`
(PowerShell 7.3+, module `Microsoft.Graph`). Both create the app registration, a self-signed RSA-3072 certificate
(or take yours: `--cert/--key`, `-CertFile/-KeyFile`), upload the certificate, add the application permissions of
the table below (read+write; `--backup-only` / `-BackupOnly` for the read set; `--teams-messages`, `--chats` add the
protected ones), grant admin consent, and print tenant ID, client ID, the paths of certificate and key (plus both
in one `app.pem` for further apps), the SharePoint/OneDrive hosts and the thumbprint. They write the key with mode
0600 into a new directory; delete it after pasting. The roles are looked up by name in the Microsoft Graph service
principal (no hard-coded GUIDs). Tested: `register-app.sh` with shellcheck and a dry run against a stubbed `az`;
`register-app.ps1` is untested here (no PowerShell run against a tenant yet; part of the real-tenant run below).

Manually:

1. **App registration**: Entra admin center → Applications → App registrations → *New registration*,
   "Accounts in this organizational directory only", no redirect URI. Note the **Application (client) ID** and the
   **Directory (tenant) ID** (or use the primary domain, `contoso.onmicrosoft.com`).
2. **Certificate** (RSA, 2048 bits or more; the appliance stores key and certificate sealed as source secrets):

   ```sh
   openssl req -x509 -newkey rsa:3072 -sha256 -nodes -days 730 \
     -subj "/CN=NexusBackup M365" -keyout nexus-m365.key -out nexus-m365.crt
   ```

   Upload `nexus-m365.crt` under *Certificates & secrets → Certificates*. Do **not** create a client secret. Paste
   the certificate and the (unencrypted) key into the source; delete the key file afterwards. Before the
   certificate expires, create a new one, upload it, update the source (both fields), then remove the old one.
   Validation logs the SHA-1 thumbprint the portal shows.
3. **API permissions** → *Microsoft Graph* → **Application permissions**, then *Grant admin consent*:

   | Workload | Backup | Additionally for restores |
   |---|---|---|
   | always (list users) | `User.Read.All` | |
   | Exchange mailboxes | `Mail.Read`, `Calendars.Read`, `Contacts.Read` | `Mail.ReadWrite`, `Calendars.ReadWrite`, `Contacts.ReadWrite` |
   | OneDrive, SharePoint, Teams files | `Sites.Read.All`, `Files.Read.All` | `Sites.ReadWrite.All`, `Files.ReadWrite.All` |
   | Teams | `Team.ReadBasic.All`, `Channel.ReadBasic.All` | |
   | Teams channel messages | `ChannelMessage.Read.All` (**protected API**, see below) | `Teamwork.Migrate.All`, `Channel.Create` |
   | Microsoft 365 groups (on by default; also used to tag team sites) | `Group.Read.All` (covers listing groups, their sites and conversations) | (group files: the Sites/Files permissions above) |
   | 1:1 and group chats | `Chat.Read.All` (**protected API**, metered), `Chat.ReadBasic.All` (topic, members) | (download only) |

   Application permissions are tenant-wide. To limit which mailboxes the app can read, use Exchange Online
   *RBAC for Applications* (management scope on a group) for the mail/calendar/contact permissions;
   `Sites.Selected` is not supported in v1 (site discovery needs `Sites.Read.All`).
4. **Teams channel messages** (optional, off by default): Microsoft's export API for channel messages is a
   *protected API*. Request access for the app (form linked from https://aka.ms/teamsgraph/requestaccess; it can
   take days). Choose the payment model in the source: `B` (backup use, metered — link an Azure subscription to
   the app for billing), `A` (security/compliance licences) or `evaluation` (small free monthly quota, good for a
   test tenant). Until Microsoft approves, validation reports the field **Teams: channel messages** with an
   explanation and backups of teams fail with the same message; disable the workload to back up team files only.
5. **Chats** (optional, off by default, field **Users: 1:1 and group chats**): the export API
   `GET /users/{id}/chats/getAllMessages` is a protected API like the channel messages (same request form, same
   payment model field `teams_export_model`). It is **metered**: with model `B` Microsoft bills every exported
   message to the Azure subscription linked to the app, so leave it off unless chats must be kept. Validation
   reports the field **Chats** while Microsoft has not approved the app.
6. **Further app registrations** (optional, field **Further app registrations**): Graph throttles per app and
   tenant; large tenants back up faster with 2–4 apps. Each needs the same permissions (and the same protected-API
   approval if those workloads are on); paste its client ID and its certificate *and* key in one PEM (the helper
   scripts write `app.pem`). See "Several app registrations" below.
7. **Source** (appliance, *Configuration → Sources → New source → Microsoft 365 tenant*): tenant ID, client ID,
   certificate, private key, the workloads, the **SharePoint host** (`contoso.sharepoint.com`) and the **OneDrive
   host** (`contoso-my.sharepoint.com`). *Validate connection* signs in and checks one call per enabled workload;
   wrong hosts are reported with the right value.

## Several app registrations

The source's own app (tenant ID, client ID, certificate, key) is app 1; `apps` lists up to 8 more
(`{client_id, certificate}`, the certificate field holding certificate and key; sealed like the first key and
write-only in the form). Every app of a source belongs to the same tenant: the tenant ID is the source's
(an app of another tenant could not read this tenant anyway, and a per-app tenant would let one source mix tenants).

- **Round-robin per guest:** each user/site/team starts with app `FNV-1a(guest id) mod n`, so the guests of a group
  (and parallel guests, `parallel_guests`) spread over the apps the same way every run.
- **Failover on throttling:** each app has its own token and throttle state. A `429` parks the app for its
  `Retry-After` (else exponential backoff) and the request goes out at once with the next app that is not parked;
  only when every app is parked does the plugin wait (until the first one is free again). `503`/`504` (service-side)
  are waited out as before. The backup summary counts the moves (`… app switches`).
- **Validation** signs in with every app and reads the directory with it; a failing app is reported on the field
  **Further app registrations** with its number and client ID.
- Form: items keep their sealed certificate as long as their client ID stays at the same position; removing an
  app in the middle asks for the certificates of the apps after it again (sealed secrets are bound to their position).

## Network

The manifest declares four HTTPS endpoints; the scheduler adds them to the appliance's outbound allow-list and
the sandbox lets the plugin connect to their ports only:

| Endpoint | Host | Why |
|---|---|---|
| `graph_host` | `graph.microsoft.com` (fixed default, contract v1.3 `default_host`) | all API calls |
| `login_host` | `login.microsoftonline.com` (fixed default) | tokens |
| `sharepoint_host` | `<tenant>.sharepoint.com` (config) | file downloads (Graph redirects there) and upload sessions of sites and teams |
| `onedrive_host` | `<tenant>-my.sharepoint.com` (config) | the same for OneDrive |

`graph_host`, `login_host` and `port` (443) only need values for national clouds or test setups; `ca_cert` adds a
CA (test setups, TLS-inspecting proxies) to the built-in public web PKI roots. Like every name in the allow-list,
these hosts are resolved when the firewall syncs; Microsoft's front doors rotate addresses, so a job may meet an
address the set does not have yet (same caveat as S3, docs/s3-offsite.md "Firewall").

## Authentication

OAuth 2.0 client-credentials grant against `https://<login_host>/<tenant>/oauth2/v2.0/token` with
`scope=https://<graph_host>/.default` and a **client assertion**: a JWT signed with the certificate's private key
(`alg` PS256, `x5t#S256` = base64url SHA-256 of the certificate, `x5t` = SHA-1 for older endpoints; claims
`aud` = token URL, `iss` = `sub` = client id, random `jti`, `nbf`/`iat`/`exp` = now −60 s / now / +10 min). The key
is checked against the certificate before use (RSA ≥ 2048 bits, PKCS#8 or PKCS#1, unencrypted; PEM pasted into a
single-line field is repaired). Tokens are cached and renewed when less than 5 minutes remain, and once more
when Graph answers 401. Bearer tokens are only sent to the Graph origin: `@odata.nextLink`/delta links pointing
elsewhere are refused, upload-session URLs (pre-authenticated) get no token, and the redirect of downloads
drops the header when the host changes.

## Incremental backups

The previous snapshot is read back with **`BaseList`** (contract v1.3: the base snapshot's entries in path order
with full metadata). With the ids in `user.m365.id` the plugin rebuilds what it knew per item (path, version tag,
time, size) without keeping item lists in the state blob (max 1 MiB — far too small for large mailboxes). The
state blob holds only the **delta links** (`mail:<folder id>`, `drive:<drive id>`) and the start time of the last
Teams export; if it would exceed 1 MiB the longest links are dropped (those containers are listed completely next
time — that costs requests, not downloads).

| Workload | Change detection |
|---|---|
| mail | folder hierarchy: full `mailFolders/delta` each time; messages: `mailFolders/{id}/messages/delta` per folder with the stored delta link (immutable ids via `Prefer: IdType="ImmutableId"`); `@removed` = deleted or moved away |
| OneDrive, libraries, team files | `drives/{id}/root/delta` with the stored delta link; the item tree (id → parent, name) is rebuilt from the base and the changes applied (renames and moves of folders included; delta answers carry no paths) |
| calendars, contacts | complete listing each time (Graph v1.0 has no delta for non-expanded events; contacts are small), compared by id/changeKey/time |
| Teams channel messages | export API `teams/{id}/channels/getAllMessages` filtered by `lastModifiedDateTime` since the last export (10 min overlap); changed threads are re-read completely (root + replies) |
| chats | export API `users/{id}/chats/getAllMessages` filtered by `lastModifiedDateTime` since the last export (10 min overlap; the time is the version tag of the `chats` directory); changed chats are re-read completely (`chats/{id}/messages`), the others taken over from the base |

An item whose id, path, version tag, time (and size for files) equal the base entry is sent as `Unchanged`: the
host reuses its stored data. Everything else is downloaded. Consequences: a renamed or moved folder re-sends its
contents (new paths); an expired delta link (HTTP 400/404/410) falls back to a complete listing; with a delta
link, unchanged items cost no request at all.

Groups: conversations are listed completely each time; a conversation whose `lastDeliveredDateTime` is unchanged
is taken over from the base, others are re-read (threads, posts). Group calendar events are compared like user
calendars.

Skipped items (contract v1.7): an item read that still fails after the retries (any status but 404 = vanished and
401 = sign-in problem) is skipped, logged as a warning and reported to the host (`Sink::item_failed`); the snapshot
commits without it and the job ends **ok with warnings** (jobs list chip, job page banner, dashboard "warning").
A folder or calendar whose listing fails keeps the items of the base snapshot (unchanged); a drive whose delta query
fails is missing from that snapshot and listed completely next time. A container with skipped items stores its
previous delta link (none on a full round), and Teams keep the previous export start, so the next backup asks for
exactly those items again. A file whose download breaks off after its first bytes still fails the guest (the bytes
are already in the snapshot stream). If more than 100 items fail and they outnumber the items read (outage, revoked
access), the guest fails.

Robustness: throttling (429, 503, 504) is retried after `Retry-After` (else exponential backoff up to 60 s), up
to 8 attempts per request; transient connection errors and 500/502 likewise. Collections are followed through
`@odata.nextLink`. Files are downloaded in 32 MiB ranges (`Range` header, following Graph's redirect); a range
that breaks off is requested again from the current position (5 times at most). Items deleted between listing
and download are skipped (404 before the first byte). Snapshots are consistent per item (Microsoft 365 has no
point-in-time view); files that change size during their download are flagged by the SDK as inconsistent.

## Restores

- **Download** — the appliance's generic download (tar/zip) of the snapshot tree: mail `.eml`, events `.ics`,
  contacts `.vcf`, files as they are, Teams threads `.json`. Never reaches the plugin — unless a mail format other
  than `eml` is chosen (see "Mail export").
- **Restore to the original user / site / team** (`to_original`) and **to another one** (`to_other`, target = user
  UPN or id, site URL or id, team id or exact name; same object type as the snapshot). Optional `paths` (snapshot
  paths, e.g. `mail/Inbox`, `onedrive/Documents`; default everything) and `folder` (default
  `Restored <date> <time>`). Everything goes into **new** containers, so nothing is overwritten; if the folder exists
  the restore fails:
  - mail → new top-level mail folder `<folder>` with the backed-up folder tree; messages imported as MIME;
  - calendars → one new calendar `<folder> – <calendar>` per calendar; events created from the embedded Graph JSON
    **without attendees** (a restore must not send invitations; the attendees stay in the `.ics`);
  - contacts → new contact folder `<folder>` with one subfolder per backed-up folder;
  - OneDrive, team files → `<folder>/…` in the target's drive; site libraries → `<folder>/…` in the target site's
    library of the same name, else `<folder>/<library>/…` in its default library; files up to 4 MiB by one `PUT`,
    larger ones through an upload session (10 MiB fragments); always `conflictBehavior=fail`;
  - Recoverable Items → `<folder>/Restored deleted items` in the mailbox (messages imported as MIME);
  - private / shared channel files → `<folder>/…` in the site of the target team's private or shared channel with
    the same name (never into the team's main library, whose members may differ); without such a channel the
    files are skipped and counted;
  - Microsoft 365 groups → files (groups that are not teams) into `<folder>/…` of the group's drive; conversations
    and the group calendar are **download only**: Graph v1.0 documents no application permission to create group
    threads/posts (`POST /groups/{id}/threads`) or group events, so they are skipped and counted;
  - Teams threads → one new channel `<channel> (restored <date> <time>)` per backed-up channel, created in
    **migration mode**: messages are imported with their original author and time, then the migration is
    completed (also when the restore fails half-way). Deleted messages and messages not from a user (bots,
    system) are skipped and counted.

- **Into another Microsoft 365 tenant** (`to_other` with **Target source** = another Microsoft 365 source of the
  same appliance tenant; job parameter `target_source_id`, contract v1.6 `target_source`): the plugin runs with the
  target source's config and credentials (its apps, hosts, tenant), resolves the target user/site/team there and
  restores into a new folder as above. Use cases: **tenant migration** (mergers, divestitures: move mailboxes and
  files of selected users into the new tenant without a migration tool) and **disaster recovery into a new
  tenant** (the original tenant is lost, compromised or locked: register a new source for a fresh tenant and
  restore users and sites into it). Only sources of the same appliance tenant and kind are accepted (web-api and
  scheduler check it; a tenant user can only pick sources they see); the original tenant is not contacted. Teams
  channel messages are skipped there (migration import needs the original authors, users of the other tenant) and
  counted; team files are restored. The target app needs the restore permissions.
- **Chats** are download only (JSON + readable HTML per chat); Graph has no import for chat messages. A
  `to_original`/`to_other` restore skips and counts them.

## Mail export (v1.3)

The manifest's `download` restore has a `params_schema` (contract v1.9): `mail_format` = `eml` (default, the
plain download) | `mbox` | `pst`, and `pst_max_gb` (1–50, default 20). With `mbox` or `pst` the web UI sends
them as `params` of the `files_get` job; the web-api checks them against the schema, the scheduler runs
`nexus-pluginhost export` (job config without the source's secrets, `config` = `{}`), and the host starts the
plugin with **no TCP connect rule at all** (Landlock) for `Op::Export`. The plugin lists the selection
(`BaseList`), reads each file (`ReadFile`) and writes the download's files with `Output` frames; the host stages
them below `<downloads>/<token>.d/` and packs them into `<token>.tar|.zip` (docs/plugin-system.md "v1.9").

Code: `src/export.rs` (selection, formats, PST split), `src/mail.rs` (mbox, MIME → PST properties with the
`mail-parser` crate), `src/pst/` (the writer).

- **mbox**: one file per mail folder, `<folder path>.mbox` next to the folder (`mail/Inbox.mbox`,
  `mail/Inbox/Projects%2F2026.mbox`, `recoverable/Deletions.mbox`). RFC 4155 with "mboxrd" quoting: the
  separator `From <sender> <asctime UTC>` (sender = Return-Path, else From, else `MAILER-DAEMON`; date = Date
  header), every line matching `>*From ` gets one more `>`, line endings LF, a blank line after each message.
- **pst**: `<guest>.pst` (`<guest>-2.pst`, … when split); the store is named `Microsoft 365 <guest>`. The mail
  folders become folders below "Top of Personal Folders" (names decoded: `Projects%2F2026` → `Projects/2026`),
  Recoverable Items "Deletions" becomes `Recoverable Items/Deletions`, a mailbox folder "Deleted Items" is the
  PST's own. A new file is started before a message would push the current one over `pst_max_gb` (estimate: twice
  the MIME size plus the folder tables).
- Not mail (`calendar/`, `contacts/`, `onedrive/`, `chats/`, …) is copied unchanged into the archive.
- Messages larger than 512 MiB are skipped (warning; Exchange's limit is 150 MB). A message that cannot be
  parsed as MIME becomes a PST message "(message could not be parsed)" with the raw `message.eml` attached.

**PST writer** (`src/pst`, [MS-PST]; Unicode format, `bCryptMethod` none, no named properties beyond the one
entry readers expect in the name-to-id map):

- NDB (`ndb.rs`): header with both CRCs, ROOT, allocation in file order (blocks 64-byte aligned, pages 512-byte
  aligned, never across an AMap region), AMap pages with exact bitmaps (`fAMapValid` = VALID_AMAP2, `cbAMapFree`),
  PMaps (deprecated, 0xFF), FMaps / FPMaps at their intervals, a density list at 0x4200, the file grown to an
  AMap boundary; data blocks with trailer (CRC, signature), XBLOCK / XXBLOCK data trees (up to 4 GiB per node),
  SLBLOCK / SIBLOCK subnode trees, NBT and BBT built bottom-up (`cRef` 2) at the end.
- LTP (`ltp.rs`): heap-on-node with multi-block heaps (HNPAGEHDR, HNBITMAPHDR every 128 blocks, fill levels),
  BTree-on-heap with index levels, property contexts (values > 3580 bytes in subnodes, empty strings as HNID 0),
  table contexts (column layout 8/4/2/1-byte + cell existence bitmap, row index BTH, row matrix in the heap or in
  a subnode with whole rows per 8 KiB block).
- Messaging (`mod.rs`): the minimal PST of [MS-PST] 2.7 (message store with EntryIDs, name-to-id map, the six
  table templates, root folder, "Top of Personal Folders", "Deleted Items", search root, spam search folder,
  search queues) plus the folders (PC, hierarchy, contents and FAI contents tables) and messages: `IPM.Note` with
  subject, conversation topic, sender / sent-representing (name, SMTP address, one-off EntryID), display To / Cc /
  Bcc, client submit / delivery / creation / modification times, message size and flags (read, has
  attachments), importance (Importance / X-Priority), internet message ID, In-Reply-To, References, transport
  headers, plain-text body, HTML body (UTF-8, `PidTagInternetCodepage` 65001), search key; a recipient table
  (type, display name, SMTP address, one-off EntryID); attachments by value (file name, MIME type, size, data;
  inline images with content ID and hidden; attached messages as `.eml` files).

Memory and disk: messages are read and written one at a time (a message's MIME, its decoded parts and its PST
node at once: up to about 4 × the message size); the writer keeps only metadata in memory (about 60 bytes per
block and node, plus the contents-table row of each message, a few hundred bytes). On the appliance the staged
files and the archive are both in the downloads directory: at the end of a job about twice the export size
(the host removes each staged file once it is packed), plus 24 hours for the archive.

Not covered: Outlook-only properties that Graph's MIME does not carry (categories, flags, read state — messages
are exported as read), calendar items and contacts in the PST (they stay `.ics` / `.vcf`), RTF bodies, ANSI PST,
PST encryption, embedded message objects (attached messages are `.eml` attachments).

## Limits (v1.2)

- Calendars: modified or cancelled occurrences of recurring series and event attachments are not backed up;
  restored events have no attendees. Contacts: photos are not backed up. Mail: archive mailboxes and public
  folders are not covered; of Recoverable Items only "Deletions" (not "Purges", "Versions", litigation-hold data).
- Microsoft 365 groups: Graph v1.0 documents **no application permission for group calendars**; the plugin tries
  and notes "group calendar not readable" when Microsoft refuses (expected on a real tenant until that changes).
  Conversations are backed up, but restores of conversations and group events are download-only (no application
  permission to create them). Group conversation attachments are not fetched separately (the posts' JSON only).
- Files: only the current version (no version history), no permissions/sharing links, no SharePoint lists, no
  subsites, no OneNote-specific handling (notebooks are folders). One SharePoint host and one OneDrive host per
  source (no multi-geo, no vanity domains).
- Teams: private and shared channel files are backed up under the team (`channel-files/`); shared channels that
  other teams share *into* this one are not (they belong to their host team). Channel messages of private/shared
  channels come from the same export API as standard ones. Meeting recordings, inline images
  (hosted contents) and tabs are not covered. Chats: text and metadata only (no hosted images or files shared in
  chats — those live in the sender's OneDrive).
- Skipped items: a download that breaks off after its first bytes is not skippable (the guest fails); items that
  vanish between listing and download are skipped silently (counted in the log, not as warnings).
- Folder renames re-download the folder's contents.
