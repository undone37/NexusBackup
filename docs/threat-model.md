# Threat Model (v0.2)

Scope: the appliance, its sources and the offsite tier, as described in `plan.md`.
v0.2 (2026-10-09): updated after the internal security review
(`docs/security-review.md`); T12/T13 added, mitigations point to code, residual
risks reflect the current implementation. External test scope: `docs/pentest-scope.md`.

## Assets
1. Backup data and indexes (confidentiality, integrity, availability).
2. Tenant DEKs, appliance KEK, recovery key.
3. Credentials the appliance holds for sources and Storage Boxes (tier-0).
4. Retention guarantees (locks, compliance clock, quorum, audit log).
5. Root on the protected PVE nodes (the node plugin runs as root).

## Adversaries and mitigations

| # | Adversary / scenario | Goal | Mitigations | Residual risk |
|---|---|---|---|---|
| T1 | Ransomware on a source (PVE node, server) | Destroy or encrypt backups | Pull model: sources hold no appliance credentials and the appliance has no inbound data port; SSH `restrict`/forced command with strict argument regexes (`pve-plugin/helper`). | Encrypted data gets backed up; detected by the change-rate and file-level anomaly checks (Phases 13e, 21a: ransom-note names, mass renames), which flag the snapshot so restores and holds default to the latest clean one (T33). A slow or name-preserving encryption below the thresholds is not detected. |
| T2 | Compromised admin account | Delete backups, shorten retention, stop offsite | Locks only extendable (`Store::extend_lock`/`delete_snapshot`); quorum (when approvals are enabled) for destructive/weakening actions incl. group moves, tenant offsite changes, privileged account changes, replication peers and DEK exports, large GC; approvers are admins and security officers, never the requester; disabling approvals needs a second person, enabling is immediate; changes that would leave fewer than two possible approvers are refused; stale approvals refused; write-only secrets do not follow endpoint changes; self-enrollment: admins never learn another user's password or TOTP seed (one-time activation code, privileged accounts with a code split between requester and approver); TOTP; re-authentication for credential changes; hash-chained audit log; RBAC matrix test. | Two colluding approvers; admin can still stop *future* backups (remove guests from groups, break source config) — detected by the lag/failed-job alerts, not prevented. **Approvals disabled** (default with a single administrator, plan §2): one admin can weaken policies, delete groups/sources/tenants, run a large GC (explicit, audited confirmation) and export DEKs to a replication peer — retention locks still protect existing snapshots, every action is audited with `"approvals": "disabled"`, and the dashboard recommends enabling approvals once two people could approve. Accounts created while approvals were off were provisioned by one person (review them after enabling). Approvers must verify out of band that a new or promoted account belongs to the named person. |
| T3 | System time manipulation (`date`, rogue NTP) | Expire locks early | Compliance clock with bounded forward slew (ADR-011, 0.1 % since Phase 18), non-finite values refused; NTS for chrony; `clock_skew` alert and diag check `time.compliance` make a jump visible. | +0.1 % drift (≈ 20 min per 14-day lock); deleting the clock file (uid `nexus-chunkstore` or root) re-trusts system time once; TPM NV counter later. |
| T4 | Storage provider / Storage Box compromise (passive) | Read or fingerprint data | Per-tenant keyed chunk IDs, AEAD on everything (AAD binds tenant + context), meaningless file names. | Traffic and size analysis (compression before encryption leaks sizes). |
| T5 | Storage Box deletion (by a compromised appliance) | Destroy the offsite copy | Box snapshots set up in the Hetzner console (no API key on the appliance); offsite inventory monitoring. S3 targets: Object Lock in compliance mode on every pack, snapshot file and key escrow file (until the snapshot's offsite lock), credentials without `DeleteObjectVersion`/bucket changes, deletes only add markers (docs/s3-offsite.md). | Storage Box: ~6-week detection window. S3: unlocked data only for the lifecycle delay; lock extension to absurd dates (cost); provider without real compliance semantics. |
| T6 | Compromised appliance (root) | Reach the whole infrastructure | Least-privilege source credentials, separate management network, SELinux domains, no interactive root (only the audited, time-limited console gate, T17), nftables egress allow-list. | Source data readable within scope (inherent to the pull model); root on PVE nodes via restore (T13). Several services share one uid today (review H-3). |
| T7 | Disk / hardware theft, physical console access | Read data; root via the boot loader | Chunk AEAD; LUKS2 + TPM **deferred**. Boot loader locked (Phase 18): GRUB superuser password for editing entries / the command line, no passwordless rescue, emergency or initramfs shell (see T18). | KEK is a plain 0600 file (review H-1): disk theft = all tenant data. Cold-boot attack. Without disk encryption, booting another medium (firmware not locked) reads the disk; the GRUB password only closes the boot-loader path. |
| T8 | Bit rot / tampered chunks | Silent corruption | AEAD tag + keyed-hash re-check on every read; rolling verify; offsite sampled verify. | Corruption is detected, not repaired, without a second copy. |
| T9 | Crash / power loss during a write | Corrupt store | Commit protocol (ADR-012), GC aborts on an unreadable manifest/index, grace period. | Backups longer than the grace period. |
| T10 | Malicious agent / NBD / SFTP peer, malicious guest content | Exploit parsers, plant files on the user's machine | Rust, cargo-fuzz targets for every network-facing parser (`crates/*/fuzz`, `lab/fuzz/run.sh`), mTLS for agents (later), restore micro-VM for foreign file systems, file-restore downloads drop `..`/NUL names and entries below symlinks. | Kernel NBD/FS bugs (confined to the micro-VM, but QEMU shares the scheduler uid today); restored disks are parsed by the node kernel (`/dev/nbdX`); unbounded tar long names / NBD extent lists (memory DoS of one job). |
| T11 | Path traversal via source / index names | Write outside the store | `check_name` allows only `[A-Za-z0-9._-]` without a leading dot; offsite listings validated the same way (pack ids = 32 hex). | — |
| T12 | Malicious Storage Box (active: crafted listings, packs, footers, extra files) | Crash DR/verify, plant data, cause local data loss | Every pack index / manifest / index authenticated before use, only files named by the authenticated manifest are kept, foreign names reported as unknown, footers range-checked, downloads bounded by the recorded pack size; fuzz target `hostile_box` asserts no local loss and no writes outside the state dir. | Denial of DR / offsite (the box can delete anyway, T5); memory DoS via huge manifests. |
| T13 | Stolen appliance SSH key (helper user `nexusbackup`) or compromised appliance → PVE node | Root on the node | Forced command + `restrict`, root-owned `authorized_keys`; sticky rendezvous and state dirs; root writes only into root-owned dirs with `O_EXCL|O_NOFOLLOW`; restore drops `lxc.*`/`args`/`hookscript` keys from catalog configs; CT staging dir must be a private root-owned dir. | Helper can still DoS jobs (predictable names) and read the live NBD export it is given; restored guest disks touch the node kernel (`/dev/nbdX`, udev, LVM autoactivation); no `from=` restriction in `authorized_keys` by default. |

| T14 | Replication (docs/replication.md): compromised secondary, compromised primary, network attacker between them, stolen peer certificate | Read other tenants, destroy the replicated copy, obtain DEKs | Secondary pulls (primary holds no credentials for it); mTLS with certificates of the primary's own replication CA, fingerprint re-checked per request (revocation immediate), tenant scope per peer enforced by web-api and replicad; peer API only on the replication ALPN; replicad reads stores read-only, has no keys/network; DEKs only sealed to the secondary keyd's X25519 key after a second quorum approval naming that key; enrollment = one-time code + pinned primary certificate + TLS-exporter-bound proofs (MITM test); every received object verified before import, manifest last; secondary never deletes because the primary did. | A compromised secondary reads its scoped tenants (inherent). A compromised web-api on the primary could ask replicad for any tenant's *sealed* objects. A malicious primary can stop serving or serve garbage (failed sync + alert) and push newer DEK versions for its own tenants. Listing reveals source names and times of scoped tenants. Same uid for replicad and the scheduler (H-3): MAC is the boundary. |

| T15 | OIDC (Phase 12, docs/phase12-contract.md §2): compromised or misconfigured IdP, IdP admin, network attacker, attacker web page | Sign in as an appliance admin; plant a session (login CSRF); redirect users elsewhere | The IdP is a trust anchor for every account it maps: changing the OIDC settings (issuer, client, mappings) needs a quorum approval while approvals are enabled; ID tokens checked strictly (RS256/ES256/PS256 only, never `none`/HMAC; `iss`, `aud`/`azp`, `exp`/`iat`/`nbf` ±60 s, `nonce`); authorization code + PKCE S256, one-use `state` bound to the browser by an HttpOnly cookie; discovery issuer must equal the configured issuer; https only (http for loopback); no redirects followed, answers ≤ 1 MiB; `next` same-origin paths only; local account names are never taken over; no mapping → account disabled; refusals audited and rate-limited per address; local admins remain as break-glass (MFA for OIDC accounts is the IdP's job). | Whoever controls the IdP or its group membership controls the mapped roles — including admin and security officer, **without** the appliance's quorum for privileged grants (the quorum covers only the mapping itself); two "approvers" may be one IdP admin. IdP-driven demotions are not checked against the "two possible approvers" rule. A key removed from the IdP's JWKS stays trusted up to 1 h (discovery cache). The client secret is readable by the web-api uid (it sends it). Filling the pending-login table (10 000 entries, 10 min) blocks OIDC sign-in (local login unaffected). |
| T16 | Break-glass (`nexus-setup recover-admin`, §7) misused by someone at the console | Take over an admin account | Needs root on the console **and** the recovery key; refused with two or more possible approvers unless `--force-solo`; audited (`user.break_glass`), critical alert delivered by the alert channels, banner in the UI until an admin or security officer acknowledges it; the code is shown once and expires after 72 h. | Root + recovery key = full control anyway (the recovery key also opens all data, T7); detection, not prevention. |
| T17 | Diagnostics (Phase 14b): a support bundle leaves the appliance; an admin session is hijacked; the root helper `nexus-diag` is abused | Leak secrets or infrastructure details; read keys through the root helper | Bundles only for admins, downloadable by the requester for 24 h, audited (`diag.bundle`, `download.get`); every file passes `redact()` (PEM blocks, auth headers, cookies, tokens, password/secret/key fields, URL passwords, TOTP secrets; unit-tested); catalog statistics are row counts only. `nexus-diag` takes a 4 KiB JSON request (id 32 hex, kind, user, bounded range) read with `O_NOFOLLOW`; runs in `nexus_diag_t`: no inet sockets (`neverallow`, `IPAddressDeny=any`), no keyd socket, no keys/stores/credentials/job configs (`neverallow`), writes only its control dir; the policy grants it no capabilities, so DAC keeps the TLS key (0600 nexus-webapi) closed. | Host names and IP addresses stay in the bundle (documented, needed for support); redaction is pattern-based, a secret in an unknown format can pass; the journal itself is readable by the helper; the metrics token shares its type with the web certificate. |
| T18 | Emergency console root shell (Phase 14c, `nexus-console-gate` on tty2) misused: an admin alone, someone at the console with a stolen code, guessing, a compromised service forging codes | Root on the appliance | Physical/hypervisor console only (no network path). One-time code only after a **second person** approved `console.unlock` (approvals enabled), shown once to the requester, only its SHA-256 on disk, valid 24 h after the approval, revocable; 100-bit codes, 5 attempts / 15 min with backoff, every failure audited. Recovery key as the fallback (the key opens all data anyway, T7). Shell ≤ 8 h (systemd scope `RuntimeMaxSec`), audited start/end, critical alerts (`console_unlock`, `console_root_shell`), banner in the UI while it runs. No way around the gate at boot (Phase 18): editing GRUB entries or its command line (`init=/bin/sh`, `rd.break`, `systemd.unit=`, `systemd.setenv=`) needs the GRUB superuser password, derived from the recovery key (normal boots stay unattended, entries unrestricted); `rescue.target` masked, emergency mode's sulogin refuses the locked root (`SYSTEMD_SULOGIN_FORCE=0`), no initramfs shell (`rd.shell=0`). SELinux: only `nexus_consolegate_t` may transition to `unconfined_t` and only by executing a shell; only the web-api domain can create unlock files, only it and the gate read them (neverallow, checked at image build). | With approvals disabled one admin + console access = root (audited, alerted). The shell itself is unconfined root: what is done in it is not audited command by command and it can switch off the time limit, the audit and the alerts (detection relies on the alert having been delivered first). Whoever controls the hypervisor console, the firmware or the boot medium also controls the machine (boot another system, read the disk: T7); the GRUB password does not protect firmware settings (set a firmware password on real hardware). The web-api domain can issue a code without an approval only by bypassing its own checks (a web-api compromise already reaches the catalog). |
| T19 | Stolen API token (script host, CI log, leaked secret store) | Act as the token's user from anywhere on the management network | Tokens expire (≤ 365 days), are scoped (read / operator) and capped by the user's role; an allow-list keeps them away from approvals, settings, users, tokens, plugins, certificates, downloads (also `files_get` / mount jobs), key exports and deletes; creating one needs re-authentication; only the SHA-256 is stored; last use (time, IP) shown; revocable by the user and admins; audited as `<user> via token <name>`; dead with a disabled user. | An operator token can start restores (incl. replace-style restores to targets the role allows) and cancel jobs until it expires or is revoked; no IP binding. |
| T20 | Admin session or account abused to install a rogue web certificate | Intercept browser sessions with a certificate the attacker controls | The key is generated by `nexus-tls` (root) and never leaves the appliance, so an imported certificate is only usable with that key; the chain is validated (key, order, dates, names, usage); `tls.install` is audited; replication keeps its pinned identity certificate. | An attacker who is admin can still revert to self-signed (browsers warn again) or get a CSR signed by a CA the clients trust; no approval required. |
| T21 | Root or a catalog writer (compromised scheduler / web-api uid) rewriting history; an admin silencing the trail (Phase 14a) | Hide actions by rebuilding the audit chain; stop the audit trail from leaving the box | Forwarding (`scheduler/src/forward.rs`): every audit entry with `seq` + `hash`, alert events and finished jobs go to syslog over TLS (RFC 5424/5425) and/or HTTPS JSON, in order and at least once (cursor per sink advanced only after a delivered batch); TLS verified against a CA, an exact certificate or a SHA-256 pin, no "insecure" switch; daily `audit.anchor` entry (head seq + hash) so the head leaves the box at least daily; a failing sink raises `forwarding:<sink>` after 15 min; disabling / removing an enabled sink or changing its destination, trust or headers needs quorum (`settings.forwarding`); egress only to the configured sinks (allow-list); header secrets sealed to the scheduler; `audit.export` audited. | Entries written and rewritten before they were forwarded (forwarding lags by seconds; up to a day for the anchor if the sink was down) cannot be told apart; the receiver must keep what it got (WORM/SIEM retention is the customer's). Syslog has no application acknowledgement (a clean TLS close counts as delivered); duplicates after a failure (dedupe by `seq` / `outbox_seq`). With approvals disabled one admin can switch forwarding off (audited locally; the entry itself may not be forwarded any more: the receiver should alert when the daily `audit.anchor` stops arriving). Root can stop the scheduler. The SD-ID uses the documentation PEN 32473 until an enterprise number is assigned. |
| T22 | Compromised admin or security officer account vs. legal holds (Phase 15c) | Remove evidence: release a hold and let retention prune; prevent holds | Holds live in the catalog and are enforced by the scheduler for local, orphan, offsite and replica retention, GC (mark over existing snapshots) and `snapshot.delete`; only security officers set holds (additive, immediate, audited); releasing is a quorum action (`snapshot.hold_release`) another admin or security officer approves; the release request and approval are audited; a replication secondary never applies or releases on the primary's word (advisory only). | Two colluding approvers can release; with approvals disabled one admin or security officer can release alone (audited `"approvals": "disabled"`). A compromised security officer can put everything on hold (fills the store: capacity alert; releases need approval). Root or the scheduler uid can delete store files directly (as for any snapshot; the retention lock and offsite Object Lock remain the hard protection). A hold is not a store lock: a store opened without the catalog (offsite DR, `nexus-offsite`) does not know it. |
| T23 | Network attacker or stolen credentials used from an untrusted network; an admin opening (or closing) the appliance's inbound access (Phase 16c) | Reach the sign-in page / API / replication endpoint from anywhere on the network; lock the administrators out; hide probing | Inbound default-deny (`os/nftables.conf`); per-service source lists (`web` 8443, ping) in nftables interval sets filled only from validated CIDR literals by the root helper `nexus-nft-sync` (CAP_NET_ADMIN only, fixed set names, a file with an unknown service or CIDR is refused as a whole); every change needs quorum (`firewall.inbound`, refused if the rule changed since the request); a web list without the requester's address needs the address typed; console reset `nexus-setup reset-firewall` (root at the console only; audited, warning alert); dropped attempts recorded in bounded dynamic sets (24 h, 256 per family) and logged rate-limited (`nexus-in-drop`); the web-api only reads a status file (no nft, no journal). | The web UI, API, `/metrics` and replication share 8443 and cannot be restricted separately (TLS hides the path; ALPN is not visible to nftables). With approvals disabled one admin can open 8443 to any address or lock everybody out (console reset). Source lists are IP-based: a peer behind NAT or a proxy shares its address with everything else there. A full drop set records nothing new until elements expire.
| T24 | Admin session abused to destroy data through the disk layout (Phase 16b); the root helper `nexus-disks` abused | Overwrite disks that hold data (store, OS, foreign disks), unmount the store, read keys or backups as root | Layout changes need the typed serial numbers and approval by a second person (`disks.*`), audited; the web-api and again the helper right before acting accept only `empty` disks (no partitions, no `lsblk`/`wipefs` signature, not mounted, no array, not system, SMART not failing) and arrays named `nexus-data`/`nexus-metadata`; the data array only while the store holds no files; requests are 4 KiB JSON with validated ids, serials and UUIDs read with `O_NOFOLLOW`; `nexus_disks_t`: no inet sockets, no reads of keys, catalog, credentials or store files (`neverallow`), writes only its dir and one named mount unit. | With approvals disabled one admin can format empty disks (by design: they are empty). Root on the console is out of scope. A disk that holds data in a format neither `lsblk` nor `wipefs` recognises counts as empty (the typed serial is the last line of defence). |
| T25 | Tenant recovery key (Phase 17e) leaked, or the request abused by one admin | Read one tenant's data from its offsite copy | Optional per tenant; generated only after a `tenant.recovery_key` approval by a second person (approvals enabled), shown once to the requester, never stored (only the X25519 public key in the catalog and keyd; audit carries the key id; tested that the key is in no audit entry, quorum param, setting or alert). It opens only `keys/tenants/<t>/tenant-escrow.<kid>.*`: the sealed plaintext names the tenant and version, `kek.recovery` and other tenants are never involved, so it cannot unlock other tenants or the appliance escrow. Replacing it (approval again) stops sealing new DEK versions to the old key and deletes its offsite escrow files. | A leaked key + read access to that tenant's offsite target = all of that tenant's data up to the replacement (the offsite copy only; the attacker also needs the storage credentials or the provider). Objects under S3 Object Lock keep the old escrow until the lock ends; anyone who copied the old files keeps them. With approvals disabled one admin can obtain a key (audited). The web-api holds the key in memory while answering. |
| T26 | Attach an offsite copy (Phase 17d) abused: one admin pulls a tenant's offsite copy onto an appliance they control; the recovery key leaks through the approval flow, logs or the catalog; an attacker-controlled "target" | Read another appliance's offsite data; learn the recovery key; plant data | Quorum `tenant.attach_offsite` (another admin or security officer approves) before any egress to the target opens; the recovery key is not part of the request (approvers read params): only the requester submits it afterwards, sealed to the scheduler and bound to that request, removed from the job row when the job is planned, passed to `nexus-offsite` as a 0600 file in the scheduler's private job dir that the CLI deletes after reading, sent to keyd over its uid-checked socket and zeroized there; never audited or logged (`GET /jobs` redacts sealed values); keyd stores only the DEKs re-wrapped under its own KEK. Everything read from the target is authenticated with the unwrapped DEKs before use (T12). | Whoever holds the recovery key **and** the target credentials can read the copy anyway (by design: that is DR, T7). With approvals disabled one admin can attach alone (audited). The sealed key sits in the catalog (WAL, free pages) for the seconds until the job is planned: opening it needs the scheduler's private key. The attached tenant keeps the old escrow on the target, so the old recovery key stays valid for that copy. |
| T27 | One stolen admin (or operator) account on a replication secondary in vault mode (Phase 17c) | Read the vault copy out (restore or download every tenant), weaken it (disable approvals, open the web UI to any address, add sources to back up into it, make it a primary) or switch the vault off | Vault mode forces approvals on (`approvals.disable` refused in the web UI, at approval time and at the console); every restore, mount and download is a `vault.restore` request a second person approves, and the job then runs as the requester only (downloads stay theirs); new tenants, sources, groups, agents and peers are refused; the web inbound list must stay restricted; enabling is approved; switching off needs an approved `vault.disable` **and** the recovery key typed as root at the console (`nexus-setup vault-disable`; the web-api never talks to keyd, so it is no recovery-key oracle), audited with a warning alert. | Two colluding approvers can approve restores (audited with the job parameters). Browsing file names (`files_list`) needs no approval. Root at the console with the recovery key can switch the vault off after one approval — and can reset approver accounts with `recover-admin --force-solo` (critical alert). Deleting replication sources (approved) stops replication; the secondary's own retention still applies. |
| T28 | Admin account abused to stop a tenant's protection quietly (Phase 17f) | Deactivate a tenant so its backups stop without RPO alerts | Deactivation is a quorum action (`tenant.disable`, with a reason) another admin or security officer approves; the dashboard shows the tenant as deactivated with a banner; one info alert `tenant_disabled` stays open; retention keeps running (no snapshot is deleted early); reactivation is immediate. | With approvals disabled one admin can deactivate alone (audited `"approvals": "disabled"`). The tenant's other alerts are muted while it is deactivated. |
| T29 | Compromised primary pushing damage to the secondary; one admin on the secondary reopening the path or loosening its windows (Phase 17a/b) | Reach the secondary while the primary is suspect; keep the secondary online around the clock | The secondary pulls, so nothing reaches it outside its sync window: no firewall target, no syncs (a running one is cancelled at the window's end). "Close vault (pause pulling now)" cuts one source off at once without approval (admin or security officer, audited, alert `vault_closed`) and can only be extended; reopening is quorum `replication.reopen`; widening a sync window or loosening bandwidth windows is quorum `replication_source.update`. | With approvals disabled one admin can reopen or widen alone (audited `"approvals": "disabled"`; vault mode, T27, forces approvals on). Inside the window the primary is reachable as before. |
| T30 | Compromised or malicious tenant admin (Phase 19b, docs/control-plane.md "Tenant admins"): scope creep into other tenants or the provider plane | Read or change other tenants; promote itself; weaken its tenant's protection beyond what the provider sold; reach arbitrary hosts | One tenant per account (`users.tenant` required, OIDC mappings exactly one tenant); every write checks the object's tenant (`Ctx::owns`); accounts it creates or changes stay within `tenant_admin`/`tenant_user`/`viewer` of its tenant (never admin, security officer, operator); groups only with policies the provider assigned (re-checked when a request is approved); no policies, tenants, quota, offsite target, recovery key, snapshot delete, holds, replication, plugins, settings, approvals; its gated requests (group delete, weakening, source/agent delete) need the provider's approvers; audit view limited to its tenant; `tenant_admin_routes_classified` fails for every unclassified new route. | Within its tenant it can stop future protection (pause groups up to the pause limit, remove guests, delete sources/groups after approval, put sources into maintenance) — detected by RPO/lag alerts. Creating a source makes the appliance connect to the host it names (the egress allow-list opens automatically for source endpoints): a tenant admin can point the appliance at hosts on networks the appliance reaches (port probing / SSRF-like reach, inside the source protocols). The tenant audit view includes provider actions on the tenant's objects (names of provider staff). |
| T31 | Provider admin abusing "view as tenant" (Phase 19b) | Act inside a customer's tenant unnoticed; take tenant data out | Read-only (`viewer`) by default; acting as the tenant's admin needs approval by another admin or security officer (`tenant.impersonate`, applied to the requesting session only); never more than the admin's own role, no downloads, no API tokens while impersonating; every entry names `<admin> impersonating:<tenant>` and is visible in the tenant admins' audit view; the requester cannot approve their own requests (requested_by stays the plain name). | Read-only impersonation needs no approval (the admin can read every tenant anyway); with approvals disabled one admin can act as tenant admin alone (audited). Tenant names are visible to the provider by design. |
| T32 | Tenant re-created under a deleted tenant's name (Phase 19b) | Inherit the old tenant's offsite escrow paths, replicated copies or labels bound to the name | Tenant names and uids are immutable (catalog triggers); deleted names are tombstoned and never accepted by `POST /tenants`; replication secondaries record the primary tenant's uid at the first sync and refuse a different uid for the same name (critical `replication_verify` alert). | T33 | Leaked fleet secret (Phase 24d: GPO/Intune/Ansible configuration, MSI command line, a deployment share) or a rogue host inside a scanned range | Register a rogue agent; get it enrolled into a tenant; learn about the appliance | A fleet secret is time-limited (≤ 30 days), optionally capped (max uses), revocable at once and scoped to one tenant; only digests are stored (appliance: sealed to the scheduler; agent: `token` digest). Discovery is pull-only: the appliance scans only the admin-defined ranges (CIDR ≤ /22 resp. /118, ≤ 4096 addresses, only the agent port, rate-limited; firewall egress only to those addresses while the secret is active). Mutual HMAC proofs bound to the TLS exporter: an agent tells nothing (host name, OS) to anyone who cannot prove the secret, and the secret never crosses the wire, so a passive or active network attacker learns nothing and cannot relay. Found agents wait for an explicit **Accept** by default (auto-accept is an opt-in per secret); accept/reject/auto-accept, creation and revocation are audited; enrollment then uses the normal CSR path (the agent's key never leaves it). Admin-only creation; tenant admins accept only for their tenant. | Whoever holds the secret and an address inside a range can present a rogue agent: with manual acceptance an admin must accept it (it shows the reported host name, which the attacker chooses — check the address); with auto-accept it is enrolled into the tenant and its template group. Such an agent receives backup jobs and stores **its own** data in the tenant (quota, noise) and is offered as a restore target for that tenant's file restores (an operator restoring there would hand it data); it cannot read other hosts' backups or the appliance. A host name collision gets a suffixed name, never another agent's identity. The MSI custom action's command line carries the secret while it runs (LocalSystem only). |
| T34 | Ransomware signals abused (Phase 21a, docs/ransomware-signals.md): an attacker on the source evades or floods the checks; a compromised security officer clears a flag so restores pick an encrypted snapshot; the snapshot diff used to read another tenant's file names | Restore encrypted data as "clean"; hide an attack in alert noise; leak file names | Flags are set only by the scheduler; clearing needs the security-officer role, a note, is audited (`snapshot.anomaly_clear`, forwarded) and keeps the reason; it never resolves the alert. Removing ransom-note patterns or switching detection off needs approval (`settings.anomaly`). The diff is a job run by the scheduler with the tenant key on that tenant's sealed name indexes only (names, sizes, mtimes, no contents), restricted to the file-search roles and the user's tenant, audited (`snapshot.diff`). | One security officer can clear a flag alone (it is audited, not approved). The built-in note list and thresholds are public, so ransomware can avoid them; the change-rate rules remain. Restoring the flagged snapshot stays possible on purpose. |
| T38 | Bit rot, a failing disk or a tampered chunk file in the local store (Phase 21d, docs/control-plane.md "Health check with repair") | New backups dedup against the bad chunk, so the damage spreads into every later snapshot; a repair source (offsite target, replication primary) feeds wrong data back | Verify puts every corrupt or missing chunk on the tenant's bad-chunk list and moves a corrupt file aside: the next writer of the same plaintext stores it again, and no connector builds an incremental on a base that references a bad chunk (PVE: no devices in the node index, so fresh dirty bitmaps and a full read; agents: no base, the metadata cache is not used; plugins: no base; NAS/TrueNAS: unchanged files are re-read when a chunk is absent). Damaged snapshots are flagged (`snapshots.damaged`), audited (`snapshot.damaged` / `snapshot.repaired`) and raise a critical `snapshot_damaged` alert; offsite upload skips them. `chunk_repair` (admin) accepts a fetched chunk only after the full AEAD + keyed-hash check under the tenant key, so a compromised offsite box or primary can withhold data but cannot inject any. | Verify re-reads 1/7 of the chunks per day (missing chunks every day), so bit rot can stay unnoticed for up to a week. A backup that reuses a chunk in the moment verify moves it aside references a missing chunk until the next verify. A chunk with no offsite or primary copy is lost unless the source still has the same data. The primary cannot repair from its secondary (the secondary serves nothing; use the offsite copy). |
| T39 | Vulnerable packages in the released appliance image (Phase 21d) | Known, fixable CVEs shipped to every appliance | `release.yml` scans every release image with grype (pinned by digest, in a container) and fails on critical CVEs with a fixed package version; the full report is attached to the draft release; `cve.yml` re-scans the published channel weekly; an informational OpenSCAP CIS report is built alongside (docs/release.md "CVE scan and CIS report"). | High/medium CVEs and critical ones without a fix do not block a release (reviewed by the release manager). The scan sees packages, not the Rust binaries' crates (cargo audit / cargo deny cover those in CI). Between weekly scans a new critical CVE is unknown to us. |
