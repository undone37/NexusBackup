# MySQL / MariaDB plugin (`plugins/mysql`, Phase 23b)

Backs up MySQL 8.0 or newer and MariaDB 10.6 or newer (tested: MySQL 8.4 with Percona XtraBackup 8.4, MariaDB 11.8
with mariadb-backup) through the plugin SDK. Source kind `plugin:mysql`. User-facing setup and restore steps:
manual [04 Sources](../manual/04-sources.md#mysql-and-mariadb-mysql-80-or-newer-mariadb-106-or-newer-tested-mysql-84-mariadb-118)
and [06 Restores](../manual/06-restores.md#mysql-and-mariadb-restores). Threat model: T56.

| Group selects | Snapshot (`plugin-mysql-<source>[-<db>]`) | Restores |
|---|---|---|
| databases (guests = databases, `validate` + `guests` list them; `mysql`, `sys`, `information_schema`, `performance_schema` never offered) | one logical dump per database: stream `<db>.sql` | `to_target`: into a new (or, if asked, existing) database on the source or the alternate server; `download` |
| nothing (whole server) | `base/<n>` (backup tool's xbstream, ≤ 32 MiB pieces), `binlog/<file>/<offset>`; snapshot metadata: the recoverable range | `pitr`: new data directory on the SSH host, prepared (physical restore, `base_only`) or recovered to a time, a binlog position or the end of the snapshot; `download` |

## How (and why this way)
The plugin sandbox can only execute what the appliance image ships, so the SQL side is the MySQL client/server
protocol in Rust (`src/my.rs`: TLS via rustls, `mysql_native_password` and `caching_sha2_password`, the full
`caching_sha2` exchange only over TLS; text queries with binary-safe rows; `COM_BINLOG_DUMP`). Tools that must match
the server's version (mysqldump / mariadb-dump, mariadb-backup / xtrabackup, mysqlbinlog) run on the database host
over SSH (`src/ssh.rs`, russh, host key pinned). No new crates: all were already in the workspace.

- **Logical dump** (`src/dump.rs`), `dump_via`:
  - `ssh` (default when SSH is configured): `mysqldump` / `mariadb-dump --single-transaction --routines --triggers
    --events --hex-blob` on the database host;
  - `connection`: generated by the plugin in one `REPEATABLE READ` transaction `WITH CONSISTENT SNAPSHOT` (what
    `--single-transaction` does): tables (`SHOW CREATE TABLE`, `INSERT`s of ≤ 1 MiB), MariaDB sequences, views
    (stand-ins first, like mysqldump), routines, triggers (after the data), events, each under its own `sql_mode`.
    Works without SSH (managed databases).

  Both write a plain SQL script (`mysql <db> < <db>.sql` works on a download) behind a `-- nexus: {charset,
  collation}` header line. Tables of non-transactional engines (MyISAM, Aria, MEMORY) are named in a warning and the
  snapshot is marked not application-consistent. The restore splits the script like the `mysql` client does (quotes,
  comments, `/*!…*/` code, `DELIMITER`) and runs it statement by statement over TLS; an existing target database is
  refused unless `into_existing`; on failure a database the restore created is dropped again. The `alternate` server
  (`restore_host`/`restore_port`/`restore_user`/`restore_password`) is "another server".
- **Server backup** (`src/physical.rs`): `mariadb-backup` / `xtrabackup --backup --stream=xbstream` over SSH (the
  password reaches it in a 0600 temporary option file fed through stdin, never on a command line), cut into `base/`
  pieces; the base backup's binlog position is parsed from the tool's output. Then the binary log is pulled over the
  connection like `mysqlbinlog --read-from-remote-server --raw` (non-blocking `COM_BINLOG_DUMP` with checksums and
  the MariaDB capability announced), stored as byte ranges of the server's files so the restore rebuilds them
  exactly; each event must continue the previous one. Incremental runs re-reference `base/` and earlier binlog
  pieces (`Unchanged`) and pull only the new binlog (an idle run: `+0 pieces`), so `every 15m` schedules are cheap.
  A new base backup is taken every `full_every_days` (default 7), when the server identity changed (failover:
  `server_uuid` / `server_id`), or when the binlog the next pull needs was purged (MySQL has no replication slot:
  `binlog_expire_logs_seconds` must exceed the backup interval).
- **Recoverable range** (snapshot metadata, protocol v1.8 `SnapshotMeta`, same shape as PostgreSQL):
  `{"recoverable": {"unit": "binlog", from_time, from_lsn, to_time, to_lsn}}` with binlog positions as
  `file:position`: server time right after the base backup → server time taken right before the pull. The appliance
  stores it in `snapshots.meta`; the restore dialog shows it and bounds its time picker.
- **Physical / point-in-time restore** (`src/pitr.rs`): over SSH into a new directory (refused if it exists):
  `mbstream -x` / `xbstream -x`, `--prepare`; unless `base_only`, the binlog files are rebuilt into
  `<dir>/.nexus-binlog/`, a temporary server is started on the directory (Unix socket inside it only,
  `--skip-networking`, `--skip-grant-tables`, no binlog), `mysqlbinlog --start-position=<base position>
  [--stop-datetime | --stop-position] … | mysql` replays to the target, the server is shut down and the helper
  files removed. A target time outside the recoverable range is refused. The result is a stopped data directory
  owned by the SSH user; start a server of the same version on it. MySQL with `gtid_mode = ON` is replayed with
  `--skip-gtids`.

## Server setup
See manual 04 for the full `GRANT` list. In short: an account with `SELECT, SHOW VIEW, TRIGGER, EVENT, LOCK TABLES`
(dumps), `PROCESS, RELOAD, REPLICATION CLIENT, REPLICATION SLAVE` and `BACKUP_ADMIN` (MySQL) / `BINLOG MONITOR`
(MariaDB) for server backups, and the DDL/DML privileges for dump restores. Server backups need binary logging
(`binlog_format = ROW` recommended, a `server_id`) and SSH as the OS user that reads the data directory (normally
`mysql`), with the backup tool and, for PITR, `mysqlbinlog` / `mariadb-binlog` installed there.

## Limits
Galera / Group Replication: the plugin backs up the one server it is given (no primary selection as in the
PostgreSQL plugin). No restore into a running server. Purged binlog leaves a gap until the next base backup. The
dump restore needs `SET_ANY_DEFINER` / `SET USER` for objects of other accounts; objects of an account with
`SYSTEM_USER` can only be restored by such an account.

## Tests
`cargo test -p mysql`: unit tests (protocol packets and scrambles, quoting, dump values and the statement splitter,
tool output parsing, time and position parsing, binlog piece checks), and with rootless podman the integration test
`tests/mysql.rs` against `testbox/run.sh` (MariaDB 11 + mariadb-backup and MySQL 8.4 + XtraBackup 8.4, each with
sshd, TLS from a test CA, binlog on): validate (good and bad password, TLS, host key), guests, dumps over the
connection and over SSH restored to the source and the alternate account and compared with the server's own dump
tool, restore into an existing database, full + incremental + idle server backups (recoverable range), then PITR to
a time, to a binlog position, to the end and base only, each checked by starting a server on the restored directory.
Git worktrees and CI checkouts get their own container names and ports (`cksum` of the checkout path, as in the
PostgreSQL testbox); `NAME=… MARIADB_PORT=… MYSQL_PORT=…` override them, `NEXUS_MY_TESTBOX=skip` skips the test.

## Packaging
As the PostgreSQL plugin: build against glibc ≤ 2.39 or for musl, `nexus-plugin pack manifest.json <binary>
mysql-1.0.0.nxplugin`, sign (docs/plugin-sdk.md, lab/appliance/plugins.sh).
