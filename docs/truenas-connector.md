# TrueNAS connector

Status: v1 (2026-10-09). Decision (plan.md §2, §7.5): ZFS snapshot via the TrueNAS API, changed files
streamed from `.zfs/snapshot/<snap>` over a restricted SSH user with a forced command, no mounts on the
appliance, nothing installed on TrueNAS beyond a key; the appliance initiates everything (pull).

Tested against **TrueNAS Community Edition 25.10.7** ("Goldeye", the current stable release on
2026-10-09; 26.0 is in beta). Crate `crates/truenas` (binary `nexus-truenas`), lab `lab/truenas/`.

## 1. Research findings

Sources: the middleware of the exact release (`truenas/middleware` tag `TS-25.10.7`), the 25.10.7 ISO,
OpenZFS 2.3 `libzfs_diff.c`, and the lab VM.

### API
- The REST API (`/api/v2.0`) is deprecated since 25.04 (still present in 25.10). Current: **JSON-RPC 2.0
  over WebSocket** at `wss://<host>/api/current` (versioned aliases `/api/v25.10.x`). The connector uses it
  with five methods: `auth.login_ex`, `pool.dataset.query`, `pool.snapshot.query`, `pool.snapshot.create`,
  `pool.snapshot.delete` (none of them is a job).
- **API keys** (25.04+) belong to a user and carry exactly that user's privilege roles;
  `api_key.create` refuses users without roles ("User lacks privilege role membership"). Keys used over
  plain HTTP are revoked by TrueNAS; the connector only speaks `wss` with a pinned certificate.
  Login: `auth.login_ex {mechanism: API_KEY_PLAIN, username, api_key}`.
- **Least-privilege roles** (role.py, plugins/pool_/snapshot.py): `SNAPSHOT_WRITE` (create; includes
  `SNAPSHOT_READ` for query), `SNAPSHOT_DELETE` (a separate role: delete), `DATASET_READ`
  (`pool.dataset.query`). Nothing else. Verified in the lab with a privilege holding only these three.
- **Certificates**: 25.10 removed the built-in CA. The default certificate `truenas_default` is
  self-signed with CN/SAN `localhost`, so host name validation cannot work: the source stores the
  TrueNAS certificate itself and the connector **pins** it (exact DER match, handshake signature checked).
  A PEM of the issuing CA works too (then the host name must match). Public CAs are never trusted.

### SSH key management and the forced command
- The user field "SSH public key" (`user.sshpubkey`) is written **verbatim** to `~/.ssh/authorized_keys`
  (`account.py update_sshpubkey`: strip, write, 0600 owner; read back from the file by `user_extend`).
  There is no key format validation, so `authorized_keys` options **survive** TrueNAS's key management:
  `restrict,from="…",command="…" ssh-ed25519 …`. Verified: a 1.9 KB line set through the API round-trips
  unchanged, sshd honours it (lab probes: shell, sftp, tty, port forwarding all refused).
- Constraints: a non-root user needs a home directory on a pool dataset (sshpubkey is refused for
  `/var/empty`); `authorized_keys` is owned by the user (a forced-command escape could rewrite it — but
  see the privilege note below); the login shell must not be `nologin` (sshd runs the forced command via
  the shell; the command re-execs `/usr/bin/bash` itself).
- sshd_config is generated by the middleware: no `AllowUsers`, root key login allowed, forwarding per
  setting; extra lines can be added under "Auxiliary Parameters" (optional hardening: a root-owned
  `Match User nexusbackup` + `ForceCommand` duplicate of the command).
- `sudo` rules come from the user fields "Allowed sudo commands (no password)" and are regenerated from
  the configuration database at boot (survive upgrades). Argument-restricted sudo rules with wildcards are
  unsafe (`*` matches spaces), so the rules name plain binaries.

### ZFS permissions (`zfs allow`)
- `zfs diff` as non-root fails ("The sys_mount privilege or diff delegated permission is needed").
  The **minimal delegation is `diff`** alone (`zfs allow -u nexusbackup diff tank/data`, Local+Descendent):
  snapshots are created/deleted through the API, `hold`/`send`/`snapshot` are not needed; `zfs get`
  works without delegation (`/dev/zfs` is 0666).
- But `zfs diff` also stats `<mountpoint>/.zfs/shares/`, which fails when the user may not traverse the
  dataset root — the normal case for SMB datasets (NFSv4 ACL of the SMB preset): "Cannot stat
  /mnt/tank/smb/.zfs/shares/: unable to generate diffs" (lab).
- Delegations are stored in the pool, not the boot environment: they survive upgrades and pool
  export/import (by uid). The 25.10.7 middleware never touches them (no allow/unallow anywhere). Setting
  them needs a shell (unsupported by TrueNAS, but persistent).
- Therefore the default is **`zfs diff` through sudo** (`zfs_sudo: true`, no shell step needed);
  `zfs_sudo: false` uses the delegation (and needs traverse permission on every dataset root).

### Reading the files and the privilege it implies
Files the user cannot read (modes, POSIX/NFSv4 ACLs, other owners) are the norm on a NAS, so reading needs
root: `find`, `tar`, `realpath` run via `sudo -n`. These tools are root-equivalent if one could call them
freely, so **the security boundary is the forced command**, not the uid: it only accepts four operations
with validated arguments, only reads below `.zfs/snapshot/<nexus snapshot>` of configured datasets, and
refuses any path that is not literally canonical (no `..`, no symlink in any component — a user's symlink
to `/` inside a share cannot redirect the privileged `tar`). Alternatives considered: root's own key with
the same forced command (equivalent boundary; root's home is on the boot pool and TrueNAS discourages root
logins), granting the user read ACLs on all data (intrusive, incomplete for files with explicit ACLs),
`zfs send` (block level, no file view). **Flagged for a user decision** (see §8): accept "sudo for
find/tar/realpath/zfs behind a forced command" as the v1 model.

### Tools available on TrueNAS 25.10.7
GNU tar 1.34, GNU findutils 4.9.0, coreutils `realpath`/`xargs`, bash 5.2, OpenZFS 2.3.9, sudo,
getfattr/setfacl/nfs4xdr_getfacl, python3. The connector needs only the first five.
`tar --xattrs --xattrs-include='*'` records `system.posix_acl_access`/`_default`, `system.nfs4_acl_xdr`
(NFSv4 ACLs, raw XDR) and `user.*` (lab: compared byte-exact with `getfattr -e hex`).

### `zfs diff` output details (parser `crates/truenas/src/diff.rs`)
`-FH`: `<change>\t<type>\t<path>[\t<path2>|\t(+N)]`; paths prefixed with the dataset mount point; bytes
outside 0x21..0x7e and `\` escaped as `\` + 4 octal digits; the root directory is reported as
`<mountpoint>/`; a renamed directory is one `R` line (its content is not listed); a rename of one name
of a hard-linked file can appear as `M` of another name; rename + modification is `R` only; link count
changes are `M … (+N)`.

### Unattended install
The 25.10 ISO runs the installer's own JSON-RPC server on port 8080 (`truenas_installer --server`:
`adopt`, `list_disks`, `install {disks, set_pmbr, authentication}`), so the lab installs without console
interaction (`lab/truenas/install.py`).

## 2. Design

```
appliance (nexus-truenas, spawned by the scheduler)                TrueNAS
  API  wss://host/api/current (pinned cert, API key) ─────────────> middleware
       pool.dataset.query / pool.snapshot.create|query|delete
  SSH  ssh -l nexusbackup (pinned host key, key from job dir) ─────> sshd → forced command (bash)
       hello | diff <ds> <ref> <snap> | walk <ds> <snap> | read <ds> <snap> (+ paths on stdin)
                                                                       sudo zfs diff / find / tar
```

**Run** (`backup.rs`), one job per source (exclusive per source):
1. Expand the group's datasets (roots, and with `recursive` every mounted child; zvols and unmounted
   children are skipped, an unmounted root fails). Time `T` = now (> every previous snapshot).
2. One atomic snapshot per root: `pool.snapshot.create {dataset, name: nexus-<source>-<T>, recursive}`.
3. Per dataset: the **reference** is the last committed store snapshot `nas-<source>-<ds>` if
   `nexus-<source>-<Tprev>` still exists on TrueNAS; else a full read (logged).
   `diff` (reference → new), `walk` (metadata of every entry), plan, `read` (contents of what must be
   read), commit `Index::Tree` as `nas-<source>-<pool.ds>/<T>` (index `tree`, same format as agent
   snapshots).
4. **Rotation**: after a successful commit every other `nexus-<source>-*` snapshot of the dataset is
   deleted (the new one is the next reference); after a failure the new snapshot is deleted and the old
   reference stays. User snapshots and other sources' snapshots are never touched. A busy (still
   automounted) snapshot is retried next run.

**Change detection** (`tree.rs`): files are matched to the previous tree by ZFS object number (inode),
which survives renames of the file and of every directory above it. A file reuses its previous keyed
chunk IDs only if (a) its object is not named by `zfs diff` (+, M, R, link changes; resolved to inodes
through the walk), (b) it was a regular file of the same size and mtime, and (c) all its chunks are still
in the store; everything else is read. Directories are re-read (xattrs/ACLs) when their object changed.
Hard links: the first name in walk order is the file, later names are `Hardlink` entries (as agents).
Without a reference everything is read (FastCDC dedup still avoids storing unchanged data twice).

**Streams** (all hostile input, threat model T12-like):
- `walk`: `find -printf '%y %m %U %G %s %T@ %C@ %i %n\0%P\0%l\0'` → strict record parser (9 numeric
  fields, NUL-terminated path and link target, ≤ 4096 bytes, valid relative paths, unique, pre-order
  parents, ≤ 50 M entries).
- `read`: GNU tar `--format=posix --no-recursion --xattrs --xattrs-include='*'` of exactly the
  requested paths → own minimal tar reader (`stream.rs`): ustar checksum, regular files and directories
  only, local PAX headers ≤ 1 MiB (`path`, `size`, `SCHILY.xattr.*` ≤ 1024 × 64 KiB), global PAX
  ignored, links/devices/GNU long names/sparse refused, zero padding only after the end marker. Every
  member must be the next requested path with the walk's type and size.
- `diff`: escape decoding, mount point prefix, valid paths; output ≤ 1 GiB.

**Forced command** (`fc.rs`, one line, generated per source, shown in the UI):
`restrict[,from="<appliance>"],command="exec /usr/bin/bash -c '<script>' nexus-fc" ssh-ed25519 … `.
The script accepts `SSH_ORIGINAL_COMMAND` matching `^[a-z]+( [A-Za-z0-9_/-]+){0,3}$` only; datasets
must be a configured root or (recursive) below one; snapshots must be `nexus-<id>-<time>`; the snapshot
directory comes from `zfs get mountpoint`/`mounted`; `read` takes NUL-separated paths, canonicalises
them with `realpath -e` (batched via xargs) and refuses any path whose canonical form differs from
`<snapdir>/<path>`. Changing the datasets changes the line (paste it again).

**Naming**: dataset names are restricted to components of `[A-Za-z0-9_-]` (no `.`, `:` or space), so
`nas-<source>-<pool.a.b>` (store source, `/` → `.`) is injective and every argument is shell-inert.
Datasets with other names are reported as failed (alert), not silently skipped.

## 3. TrueNAS setup (admin, once per TrueNAS)
All in the TrueNAS UI (or API); no shell step with the defaults.
1. **Group + user** `nexusbackup`: home directory on a dataset (e.g. `/mnt/tank/home`, "create home
   directory"), shell `bash`, password disabled, SMB access off, "Allowed sudo commands with no
   password": `/usr/bin/find`, `/usr/bin/tar`, `/usr/bin/realpath`, `/usr/sbin/zfs`.
2. **Privilege** `NexusBackup` for that group with roles `SNAPSHOT_WRITE`, `SNAPSHOT_DELETE`,
   `DATASET_READ`; no web shell.
3. **API key** for user `nexusbackup` (Credentials → API Keys).
4. **SSH service** on (key login only; password login stays off).
5. On the appliance, create a TrueNAS source: API host/port, the TrueNAS certificate (System →
   Certificates → `truenas_default`, download), user + API key, SSH host/port/user, the TrueNAS SSH host key
   (`/etc/ssh/ssh_host_ed25519_key.pub`), the appliance key pair (private key is sealed, write-only), the
   appliance address for `from=`, datasets, recursion. The source then shows the `authorized_keys` line.
6. Paste that line into the "SSH public key" field of `nexusbackup`.
Optional: `zfs_sudo: false` with `zfs allow -u nexusbackup diff <dataset>` per root (shell) and traverse
permission on each dataset root; sshd "Auxiliary Parameters" `Match User nexusbackup` /
`ForceCommand …` as a root-owned second copy of the restriction.

## 4. Appliance integration
- **Catalog v5**: source kind `truenas` (table rebuild like v4). Config: `host`, `port` (443),
  `connect_addr`, `ca_pem`, `user`, `token_secret` (API key, sealed), `ssh {host, port, user, host_key,
  key_pem (sealed), public_key, from}`, `datasets`, `recursive`, `sudo` (true), `zfs_sudo` (true).
  Secrets are bound (catalog::secret) to `host/port/connect_addr/ca_pem/user` resp.
  `ssh.host/port/user/host_key`; GET returns `token_secret_set`, `ssh.key_pem_set` and
  `authorized_keys`.
- **Groups**: guests = datasets of the source (none = all). **Jobs**: `backup {group_id}`, retention per
  dataset incl. children (prefix `nas-<id>-<ds>.`), `files_list`/`files_get` on `nas-…` snapshots.
  `restore_files` is refused (download only, §6). Backup result: per snapshot `transferred_bytes`.
- **Scheduler**: spawns `nexus-truenas <job>/truenas.json backup` (pinned cert, API key, SSH key and
  `known_hosts` built from the pinned host key as 0600 files in the job dir), file jobs without any
  TrueNAS secret; the firewall allow-list gets the API and SSH endpoints of every TrueNAS source.
- **SELinux**: job domain `nexus_truenas_t` (entered only from the scheduler): http/ssh/unreserved
  ports, `/usr/bin/ssh` in-domain, job dir, tenant store, keyd socket, downloads.
- **UI**: TrueNAS source form (write-only secrets, line to paste), dataset selection in groups,
  dashboard/snapshots for `nas-` sources (browse/download; no restore button).

## 5. CLI
`nexus-truenas <config.json> backup | check | snapshots | authorized-key <pubkey-file> [from] |
files <nas-source> <time> ls <dir> | files <nas-source> <time> get <out.tar|out.zip> <path>...`.
Output lines: `committed <source>/<time> in …: … <n> bytes transferred`, `failed <ds>: …`,
`result {json}`; exit 1 if any dataset failed.

## 6. Restore
v1 is **download only** (tar keeps owners, modes, mtimes, symlinks, hard links, xattrs incl. ACLs;
zip modes and mtimes), reusing agent-conn's tree download code. Restore into a dataset over SSH would
turn the read-only forced command into a writing one running as root on TrueNAS; doing that safely needs a
separate restore key/command confined to a target dataset (openat2-style confinement is not available
with standard tools), so it is deferred.

## 7. Lab (`lab/truenas/`)
`vm.sh fetch|install|start|stop` (ISO download + sha256 check, unattended install via the installer API,
8 GB RAM, boot disk + two data disks; API on 127.0.0.1:18444, SSH 12222), `provision.py` (pool `tank`
mirror, datasets `data` (POSIX ACLs), `data/projects`, `smb` (NFSv4), `other`, the setup of §3),
`data.sh init|modify|sums|xattrs` (odd names: newline, tab, space, backslash, UTF-8, leading dash; hard
links, symlinks to `/` and `/etc/shadow`, POSIX + NFSv4 ACLs, xattrs, root-only dir, fifo, sparse file,
64 MiB random file, 2000 small files; round 2: in-place edit, file + directory renames, deletes, new
files, new hard link, chmod/chown, xattr-only and ACL-only changes), `probe.py` (17 checks on the key),
`e2e.sh` (REST end to end), `crates/truenas/tests/lab.rs` (connector against the VM, verified sums and
xattrs). Results (2026-10-09, TrueNAS 25.10.7, dev control plane):

| run | tank/data (2028 entries) | tank/data/projects | tank/smb | duration |
|---|---|---|---|---|
| scheduled full | 2014 files read, 176.3 MB transferred, 75.5 MB new | 3.15 MB | 10.4 KB | 19 s |
| scheduled incremental | 7 files read, 2005 reused, **67.3 MB** transferred (64 MiB file changed in place), 1.4 MB new | 10.5 KB | 150 B | 2.3 s |
| no changes | 0 files read, ~190 KB (walk) | 216 B | 150 B | 1.5 s |

Downloads (tar and zip of the whole dataset) matched the sha256 of all 2014 files on TrueNAS; ACL/xattr
values matched `getfattr`; after each run TrueNAS kept exactly one `nexus-<source>-<time>` snapshot per
dataset (the last backup's).

## 8. Limitations and open points
- **Needs a decision**: the privilege model (sudo for find/tar/realpath/zfs behind the forced command,
  §1). A forced-command escape would be root on TrueNAS; the command is small, tested and fuzzed, but
  this is the trust placed in it.
- File-level only: a modified file is re-read completely (64 MiB for 1 MiB changed in the lab); sparse
  files are transferred in full (stored deduplicated).
- The dataset root directory's own metadata/ACL is not recorded (entries are relative paths); matters
  only for a future restore.
- Device nodes are recorded without major/minor (`find` has no `%r`); irrelevant on NAS shares.
- All entries of a dataset are held in memory (like agent backups); `read` holds the requested path list
  in bash arrays on TrueNAS (fine for 10⁵–10⁶ changed files).
- Dataset names with `.`, `:` or spaces are not supported (reported as failed).
- Changing the source's datasets changes the `authorized_keys` line (must be pasted again).
- The TrueNAS certificate pin breaks on certificate renewal (backups fail with a TLS error until the
  source is updated).
